# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

joyjoy is a multi-tenant **Deep Agents** platform: one **FastAPI** process serves the **React SPA** and the **`/v1` JSON/SSE API** on a single origin (`:8080`). See `ARCHITECTURE.md` for the full design; `backend/README.md` and `frontend/README.md` for per-package dev guides.

## Environment

The code lives and runs in **WSL** (`~/joyjoy`). Run all build/test/docker commands from inside WSL (`wsl -d Ubuntu bash -lc '...'`), not Windows PowerShell — the inline `VAR=value cmd` form and the toolchain (uv, docker) are Linux-side.

## Commands

Backend (`cd backend`):
```bash
uv pip install -e .                                   # deps (add '.[dev]' for pytest/ruff)
uvicorn app.main:app --host 0.0.0.0 --port 8080 --reload   # run (dev: SQLite + no-auth)
pytest                                                # all tests (asyncio mode, tests/)
pytest tests/test_prompts.py::test_name -q            # single test
ruff check app                                        # lint
alembic upgrade head                                  # DB migrations
```

Frontend (`cd frontend`):
```bash
npm install
npm run dev        # Vite :5173 (proxies /v1 → :8080, injects x-user-id: alice)
npm run build      # tsc -b && vite build → dist/
npm run check      # Biome lint + format (write)
```

Full stack / containers:
```bash
scripts/start_all.sh                                  # WSL dev: jira MCP → backend → SPA (idempotent)
docker compose up --build                             # single image (SPA baked in), :8080
COMPOSE_PROFILES=localdb,sandbox,observability docker compose up --build   # + bundled PG + sandbox + observability
docker compose -f docker-compose.dev.yml up -d        # infra ONLY (no backend); run backend on host
scripts/dev-up.sh                                     # picks baked vs infra-only from DEV_MODE in .env
```

## Architecture (the parts that span files)

- **Single process, many users.** `app/main.py` mounts one `APIRouter` per concern (`app/routes/*`) and serves the built SPA via `app.frontend()`. Tenant identity (`user_id`) + `thread_id` ride on every request; there is no per-user process.
- **Agent build + cache** (`app/agent/agent.py:_get_or_build`). Compiled deepagents graphs are cached by key `("run"|"chat", uid, model, effort, genui)`. Tools are baked at build time: per-user MCP tools (cached per user, workspace-bound) + generative-UI tools + `load_skill` (sandbox only). **Changing tool availability means changing the cache key** (e.g. `genui` gates the render tools). `_invalidate_user_cache(uid)` after any per-user skill/MCP/model/memory write.
- **Run loop + HITL** (`app/agent/runs.py`). `POST /v1/runs` streams tokens, tool calls, and approval interrupts over SSE. In run mode, `interrupt_on` gates **all** MCP/plugin tools (+ `JOYJOY_INTERRUPT_TOOLS` built-ins + sandbox `execute`); per-thread `auto_approve` bypasses.
- **Two persistence layers.** Chat **messages live only in the LangGraph checkpointer** (`app/stores/persistence.py` — SQLite dev / Postgres prod). The relational app DB (`app/db/models.py`, SQLAlchemy async) holds everything else: accounts, global catalogs, per-user skills/MCP/models, and `sessions` metadata. Don't look for messages in the relational DB.
- **DB→agent filesystem bridge** (`app/stores/dbfs.py`). The agent's `/memory/AGENTS.md` and `/skills/*` are served from the DB into its virtual FS — skills/memory are edited via DB CRUD, not loose files.
- **Frontend = external-store runtime** (`frontend/src/runtime/JoyjoyRuntimeProvider.tsx`). assistant-ui in external-store mode: the app owns chat state (zustand + a custom SSE client), not a built-in runtime. Tool calls render inline via the `TOOL_UIS` map (`components/assistant-ui/tool-uis.tsx`).
- **Generative UI.** `render_ui` (JSON kit → native `MessagePrimitive.GenerativeUI`) and `render_html` (sandboxed iframe canvas) are **native in-process `StructuredTool`s, not MCP** — server-side they're no-ops; the spec/HTML rides in the tool-call args and the frontend renders it (and it persists across reloads via those args). Gated per session by the `generative_ui` run flag.
- **Model discovery spans agent.py → routes/models.py → ProvidersPanel.tsx.** `discover_models`/`save_user_models_bulk` (`app/agent/agent.py`) let the Providers tab fetch a provider's live catalog (`POST /v1/models/config/discover`) and bulk-save a selection (`/save-bulk`), reused by both the Add dialog (multi-select) and the Edit dialog (pick-one to switch a model's deployment). Per-user model ids are `{provider}:{raw_id}` composites (`_composite_model_id`) so the same base name can exist under multiple providers without colliding with a global (bare-id) model — `save_user_model` edits an EXISTING row in place by exact id match before falling back to compositing a new one, so legacy bare ids don't get silently duplicated.
- **Prefer a provider's own LangChain package over the generic `openai`-compatible bucket.** `nvidia` (`ChatNVIDIA` from `langchain-nvidia-ai-endpoints`) was the first provider done this way (`build_model_for`'s `Provider.NVIDIA` branch, `app/core/enums.py`) instead of routing through `ChatOpenAI` + a custom `base_url` preset like OpenRouter/DeepSeek/Groq/local servers still do; `xai`/`xai_oauth` (`ChatXAI` from `langchain-xai`) followed the same pattern. The payoff: `_discover_nvidia` calls `ChatNVIDIA.get_available_models()` for REAL per-model `supports_tools`/`supports_thinking`/`supports_structured_output` flags instead of guessing capabilities from the model id string the way every other adapter has to. Apply this pattern to the next provider that ships an official LangChain integration rather than defaulting it into the generic bucket.
- **xAI (Grok) is opt-in-only, with two auth modes presented as one provider.** `Provider.XAI` (API key) and `Provider.XAI_OAUTH` (RFC 8628 device-code grant, `app/agent/xai_oauth.py`) both build via `ChatXAI`; neither is ever seeded as a `global_model` — a user must configure it themselves. The frontend never shows `xai_oauth` as its own dropdown row: `ProvidersPanel.tsx`'s single "xAI (Grok)" entry has a "Use OAuth login instead" toggle that swaps the credential form for the device-code login widget and rewrites the submitted `provider` accordingly (`effectiveProvider`) — the DB/backend still treat them as genuinely distinct providers, only the UI presents a mode switch. Reasoning-effort support is model-id-gated (`model_supports_reasoning`) because unsupported Grok models hard-400 on `reasoning_effort` instead of silently ignoring it like NVIDIA does — see the reasoning-probe gotcha below for why that distinction matters.
- **xAI OAuth tokens need refreshing on every call, not just on a cold agent build.** The compiled-agent cache (`_AGENT_CACHE`, `app/agent/agent_common.py`) has no TTL, so a cache HIT skips `build_model_for` — and with it, `_ensure_xai_oauth_fresh`'s refresh-on-build check — for as long as the entry survives. A long-idle `xai_oauth` model's access token would then silently expire with nothing left to ever refresh it (every subsequent request 403s with a stale-credential error). `_get_or_build` now calls `_ensure_xai_oauth_fresh` unconditionally before the cache lookup (cheap when not due — one timestamp compare); when a refresh *does* fire, `_persist_xai_oauth_tokens` already invalidates the user's whole agent cache as a side effect, so the `cache_get` right after naturally misses and rebuilds with the fresh token.

## Gotchas

- **Config is profile-driven.** `COMPOSE_PROFILES` is the single switch: it sets `Settings.db_mode` (`devdb` → SQLite; `localdb`/`server` → Postgres, with app data in `APP_DB_NAME` and LangGraph checkpoints in the *separate* `LANGGRAPH_CHECKPOINT_DB`) and auto-derives `sandbox_enabled`/`metrics_enabled`/`tracing_enabled` (from the `sandbox`/`observability` profiles). Separately, `DEV_MODE` toggles auth strictness — `true` → no-auth dev user (identity from `X-User-Id`); `false` → cookie/JWT auth (**the dev header is ignored**). `is_prod` is now just `not dev_mode`. `app/core/config.py` is the single source for settings.
- **Secrets are `${VAR}` refs.** Model/MCP configs in the DB/seed reference `${VAR}`, expanded at agent build from `os.environ` (`main.py` loads `.env` into `os.environ`). Keys never live in the seed; `describe_mcp` must never return the *expanded* secret. Encrypted secrets in the DB use Fernet (`CREDENTIAL_ENCRYPTION_KEY` — rotating it orphans them).
- **Prod serves the baked SPA.** The backend serves `frontend/dist` (copied into the image at build). Editing frontend source needs `vite build` + `docker compose up -d --build` to show up in the container; a hot-swapped `dist` is ephemeral.
- **Dev frontend identity.** Use `http://localhost:5173` (secure context — `crypto.randomUUID`; a raw WSL IP breaks the app). The Vite proxy injects `x-user-id: alice`, so seed a `User(id="alice")` or you stay on `/signin`.
- **MCP servers in WSL: avoid bare `npx`.** It resolves to Windows `npx` (CMD/UNC failures) — prefer `uvx`/Python MCP servers. `main.py` injects `${JOYJOY_PYTHON}`/`${JOYJOY_UVX}`/`${JOYJOY_BACKEND}` so DB MCP rows stay portable.
- **i18n is strictly typed.** Locale files are `Resources = typeof en`; a new key must be added to all 16 locales or types break.
- **`devdb` persistence in the baked stack depends on `CONTAINER_DATA_DIR`.** `docker-compose.yml`'s `backend` service derives `WORKSPACE_ROOT`/`APP_DB_PATH`/`SQLITE_CHECKPOINT_PATH` AND the `workspaces` volume mount target from the same `${CONTAINER_DATA_DIR:-/data}` — if you ever change one without the other, `devdb` mode's SQLite files land back on the container's ephemeral writable layer and get wiped on the next `docker compose up --build`.
- **`workspace_id_for` (`app/stores/sessions.py`) is the ONLY thing standing between a user and someone else's sandbox files — never resolve a workspace by `thread_id` alone.** It once regressed silently: sessions used to live in a LangGraph store namespaced `(user_id, "sessions")`, so a cross-user lookup was structurally impossible (wrong namespace = not found); a later migration to a flat `Session` table kept an ownership check but let it fall through to `return thread_id` on a mismatch instead of rejecting, so any stale/forged `thread_id` from another user's session resolved to *their* workspace. Fixed by rejecting non-owned threads outright and minting brand-new workspace ids as `{user_id}-{thread_id}` (`_mint_workspace_id`) so the sandbox volume name is structurally per-user even if a future ownership check has a bug. Also clear `localStorage["joyjoy-active-thread"]` (and any per-user-keyed UI prefs) on logout — a different account logging in on the same browser must not inherit the previous user's active thread.
- **A provider "not erroring" on an unrecognized request param is not evidence it supports that feature.** `test_model`'s reasoning-capability probe (`agent.py`) used to persist `reasoning: true` whenever a forced `reasoning_effort` call merely completed without an exception — but lenient OpenAI-compatible endpoints (NVIDIA NIM included) often silently ignore params they don't understand instead of rejecting them, so this produced false positives that then caused degraded/truncated generations in real use. The probe now requires actual visible reasoning *text* as evidence, with one deliberate exception (Azure AI Foundry's Claude endpoint returns only a thinking signature, never the text, by design).
- **A field only ever populated during live SSE streaming needs its own extraction path for reloaded (persisted) messages — reading `msg.content` on reload isn't automatically equivalent.** The live run loop calls `reasoning_text_from_message` (`agent.py`) straight off the LangChain message/chunk to stream reasoning deltas, but `_serialize_message` (`app/stores/sessions.py`, backs `GET /v1/sessions/{id}/messages`) used to skip reasoning entirely — a page refresh silently dropped every Reasoning box even though the checkpointed `AIMessage` still carried the content. Fixed by having `_serialize_message` call the same extractor and the frontend's `wireToUI` push it as a `reasoning` part (ordered first, matching live streaming's `unshift`). Any new per-message field that only shows up via the SSE path needs the equivalent reload-path plumbing or it quietly won't survive a refresh.
- **`@/components/ui/*` primitives aren't all the same underlying library — match each one's real state-attribute convention, don't assume Radix.** Several (`collapsible`, `switch`, `tooltip`) wrap **base-ui** (`@base-ui/react`), not Radix, even though `radix-ui` is still a direct dependency for a few older components (e.g. `popover.tsx`). base-ui uses presence-only attributes — `data-panel-open` on `Collapsible.Trigger`; `data-open`/`data-closed`/`data-starting-style`/`data-ending-style` on `Collapsible.Panel` — instead of Radix's `data-state="open"|"closed"`. A Tailwind selector written against the wrong convention doesn't error, it just silently never matches, which is why `tool-group.tsx`/`tool-fallback.tsx`/`reasoning.tsx`'s chevron rotation and content fade/slide animation did nothing for a long time despite looking correct. For a smooth height transition specifically, don't reuse Radix-era `@keyframes`-to-`auto` tricks (`tw-animate-css`'s `animate-collapsible-*` only checks Radix/bits/reka/kb content-height vars, none of which base-ui sets) — use base-ui's own live `--collapsible-panel-height` var with a plain `transition-[height]`, forced to `0` via `data-[starting-style]`/`data-[ending-style]`.
- **The chat composer lives OUTSIDE the scrollable message viewport, not pinned inside it.** `frontend/src/components/assistant-ui/thread.tsx`'s `ThreadRoot` used to dock the composer as a `position: sticky` child of the scrollable viewport (assistant-ui's own `ViewportFooter` pattern). Sticky-in-flow only avoids covering message content at the *exact* document-flow bottom; at any other scroll position — which is the normal resting spot after any real scroll gesture, not an edge case — it visually floats over whatever message content is in that screen band, and no reserved-margin trick fixes that. It's now a plain flex sibling after the viewport (`flex-1` on the viewport, natural height on the composer row), so flexbox geometry — not scroll position — guarantees they never share pixels. The empty/new-chat view (composer centered with the welcome heading) is a separate render path gated on `isEmpty`.
